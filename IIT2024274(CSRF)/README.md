## Overview
This module demonstrates Cross-Site Request Forgery (CSRF) on a simulated online banking application (Apex Vault Bank). A victim authenticated on the banking portal (`localhost:3000`) visits an external malicious attacker website (`localhost:4000`), which auto-submits a forged `POST` transfer request using the victim's ambient session credentials.

### (a) Vulnerable Implementation
The banking transfer route processes state-changing operations based solely on session cookie authentication without requiring proof of user intent:
```javascript
// Vulnerable route in server.js:
bankApp.post('/transfer', requireAuth, (req, res) => {
  const sender = req.session.username;
  const { recipient, amount } = req.body;

  // FLAW: Executes transfer blindly without verifying CSRF tokens!
  const result = db.transferFunds(sender, recipient, amount);
  return res.redirect('/dashboard');
});
```

### (b) Working Exploit
* **Attacker Page:** Hosted on `http://localhost:4000/claim-prize` with a hidden, auto-submitting form:
```html
<!-- Malicious payload on external domain http://localhost:4000 -->
<form id="csrfPayloadForm" action="http://localhost:3000/transfer" method="POST">
  <input type="hidden" name="recipient" value="attacker_bob" />
  <input type="hidden" name="amount" value="1000" />
</form>

<script>
  // Automatically submits upon page load!
  document.getElementById('csrfPayloadForm').submit();
</script>
```
* **Execution:**
  1. Alice logs in to Apex Vault Bank (`localhost:3000`) and receives session cookie `apex_vault_sid`.
  2. Alice visits `localhost:4000/claim-prize`.
  3. The form auto-submits. The browser automatically attaches Alice's session cookie to the cross-origin POST request.
  4. In Vulnerable Mode, the bank executes the transfer without Alice's knowledge: $1,000 is transferred to Bob Malory.

### (c) Root Cause
The web application accepted a state-changing `POST` request based entirely on **ambient browser credentials** (cookies automatically attached by the browser) without verifying secret, unpredictable proof of user intent generated by the legitimate origin.

### (d) Implemented Mitigation
**Anti-CSRF Synchronizer Token Pattern:**
```javascript
// Secure route with Synchronizer Token validation:
if (currentMode === 'MITIGATED') {
  const sessionToken = req.session.csrfToken;
  const submittedToken = req.body._csrf;

  if (!submittedToken || submittedToken !== sessionToken) {
    return res.status(403).send("403 Forbidden: Invalid or missing CSRF token!");
  }
}
```
* **Verification:**
  1. Toggle server defense to **Mitigated Mode**.
  2. The server generates an unpredictable token (`crypto.randomBytes(24).toString('hex')`) per session, embedded into legitimate forms.
  3. Replay exploit: Attacker site cannot read Alice's token due to the Same-Origin Policy (SOP).
  4. The request is rejected with **HTTP 403 Forbidden**, leaving Alice's balance intact.

### (e) Other Mitigations (Theory)
1. **SameSite Cookie Attribute (`SameSite=Strict` / `SameSite=Lax`):** Restricts browsers from sending cookies on cross-site requests, mitigating CSRF for standard web forms.
2. **Re-Authentication / Step-Up Verification:** Requiring password re-entry, 2FA OTP, or CAPTCHA before completing sensitive operations.
3. **Custom Headers & CORS Preflight:** Requiring custom HTTP headers (e.g., `X-Requested-With`, `X-CSRF-Token`) on API requests sent via JavaScript, triggering CORS preflight checks that external forms cannot bypass.
4. **Avoiding State-Changing GETs:** Ensuring `GET` requests are strictly safe and idempotent (RFC 7231).
